# 평가와 개선

평가 기준과 릴리스용 별도 사례는 `protected/`에 둡니다. 현재 초기 valuation 기준은 사용자 계획의 5축·각 3점·합계 17점과 네 독립 검토를 보존합니다. 현업 원본별 점수 예시와 평가자 설정은 실제 보정 결과를 확인하기 전까지 미보정 상태입니다.

후보 작성자는 공개 개발 사례만 받습니다. 릴리스 평가자는 별도 평가 요청과 필요한 원문을 받되 버전 이름·변경 의도를 받지 않습니다. 단일 로컬 사용자 파일 권한만으로 문맥 접근을 강제 격리할 수 없으므로 호스트가 올바른 입력 묶음을 전달해야 합니다. 강한 격리가 필요한 배포에는 별도 권한의 평가 프로세스가 필요합니다.

`evaluation.preregister`가 가설·입력·평가·변경 범위·판정 규칙을 불변 파일로 저장합니다. `assignments`는 버전 매핑을 비공개 파일에 분리하고 제시 순서를 교차합니다. `record_pair`는 실패·중단·초과를 포함한 배정 결과를 보존합니다. `verdict`는 최소 3쌍 중 2쌍 이상의 개선과 나머지 동등, 중대 퇴행 없음, 별도 과업 통과를 요구합니다. 자동 후보 수정은 2회까지이며 이후 새 문제 명세가 필요합니다.

승격자는 후보 작성자와 달라야 합니다. 평가 조건이나 설정이 바뀌면 정확한 변경 해시에 대한 사람의 승인 영수증이 필요합니다. 원인 귀속은 여러 가설이나 미확정으로 남길 수 있으며, 로그 상관관계만으로 단일 원인을 확정하지 않습니다.

합성 오류 사례의 false-positive·false-negative·반복 안정성은 `calibrate`로 계산할 수 있습니다. 이것만으로 현업 보고서 평가자의 타당성이나 사람 판정과의 일치도를 주장하지 않습니다. 운영 검토와 공통 사후 채점 비용을 분리하고, 모든 배정 사례를 분모에 포함합니다.
