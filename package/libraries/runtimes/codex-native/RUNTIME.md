# Native Codex runtime — 0.2.0-dev.1

Read `host-protocol.json`, `session-policy.json`, `reasoning-policy.json` and `capabilities.json`. Session lifecycle and scoped evidence are detailed in `docs/session-workflow.md` from the release root. This component is a portable execution contract for an actual Codex host, not an inference service or an alternative state engine. Exact installed CLI `--help`, engine schemas and discovered host tool signatures are authoritative.

## Preflight

- Locate the installed pinned professional-reports release from the active installation configuration or user-supplied release location. Do not execute an arbitrary checkout as the installed release. If no installed release exists, return `missing-installed-release`; installation is a separate engine operation.
- From that release root, invoke `python3 -m pr --help` (or its installed `professional-reports` executable) and inspect help for the commands being used. Send request JSON files in the argument positions/flags shown by that installed command. Never guess CLI flags from these docs.
- Use `load` to resolve the release, and verify exact component references through the registry. Inspect available native subagent tools. If absent, record `native-agent-tool-unavailable`; a single-agent draft is not independent review.
- Track all live child agent ids associated with this run. Enforce `active < min(6, confirmed host limit, user/session limit)` before every spawn. The package upper bound of six does not override a lower native-host limit (for example three). If capacity is unknown, probe it and schedule conservatively rather than assuming six slots. Do not restart the count on a new dispatch batch. Retain outputs and actual receipts, then actually close completed workers and preserve successful close receipts. Completed workers never resume for new tasks. Each review round uses a fresh independent reviewer; retain original identities as history and record explicit per-finding resolution or reopening evidence against current hashes. Also account for workers whose wait timed out or whose closure is unconfirmed.

## Engine/host handshake

1. `run` creates or opens the authorized run using the installed schema. Supply the mandate, cutoff, fresh source manifest and approved criteria/design references as required. `meta` produces/registers the meta-planning work, and `plan` registers/validates the concrete graph. Inspect the outputs; commands do not themselves establish semantic approval. Register actual source snapshots using the installed `source` operation and other inputs, including approved-design bytes/assets, using `snapshot` before dispatch. Preserve eligibility/cutoff metadata and measured hashes. A request reference alone does not create the input snapshot ids required by node readiness. Inspect these commands' `--help` for exact JSON and argument forms.
2. `dispatch` selects or prepares a ready work unit. Retain its engine-issued immutable attempt and dispatch identity. Do not fabricate a result to advance readiness. Read its pinned component entrypoints and only the permitted references. Supply a measured host-support JSON with available `capabilities` and `reasoning_efforts` as required by dispatch. The engine rejects unsupported requested effort; explicitly revise the plan or record an environment gap before dispatch, never claim unsupported effort.
3. Call the actual native spawn tool with `fork_context=false`, the task-scoped dispatch brief, frozen inputs and output scope. Omit `model` to inherit the current session model. Send `reasoning_effort` only as supported by the discovered host schema; keep the requested value in the run record even if unsupported. For a host exposing the current tools, the actual invocation is:

   ```javascript
   const receipt = await tools.multi_agent_v1__spawn_agent({
     message: dispatchBrief,
     fork_context: false,
     reasoning_effort: requestedEffort
   });
   ```

   Here `dispatchBrief` is the current engine-generated brief plus permitted task instructions; `requestedEffort` is read from the frozen `dispatch.node.reasoning` after planning has applied the allocation policy; never reread a stale policy intention after a plan adjustment. These names represent loaded inputs, not fabricated fixtures. Discovery is required before using this example on another host.
4. Write a binding request JSON containing the actual receipt and original dispatch/attempt identifiers in the engine's format. Set `instruction_sha256` to the returned `brief_sha256`; do not hash the response again with its added hash field. The current engine normalizes the receipt tool to `multi_agent_v1.spawn_agent`; retain the observed transport tool name separately and preserve the actual response unchanged. Invoke `bind` immediately. If binding fails, do not allow that worker's results into another attempt: close or quarantine the worker and recover through `status` and the installed engine actions.
5. Use `multi_agent_v1__wait_agent` for actual completion, with bounded waits and useful independent work between waits. Use `send_input` only for a still-active worker's same-task corrections while preserving frozen inputs; changed inputs require engine invalidation/new attempt and a fresh worker. Never resume a completed worker for new tasks. A timeout is neither failure nor completion.
6. Inspect returned artifacts and actual tool evidence. The worker must write all submitted files beneath the dispatch's `result_directory` (`work/<attempt_id>`); preserve originals elsewhere as read-only inputs. Artifact `type` values must cover the node's declared `outputs`. Create the `submit` request JSON using the current installed schema and original binding. Preserve failures, limitations, absent telemetry and unperformed checks. An agent's final sentence claiming success does not replace files, hashes or observed checks. Never turn absent checks into true booleans. The current engine uses `{id, passed, evidence}` checks: a required unperformed/error check is `passed: false` with explicit `status` and evidence of the limitation; it is not an observed numeric failure. See `host-protocol.json` for the current field mapping and re-read installed schemas.
7. Dispatch the required independent review node through the same native handshake with a fresh reviewer every round. Carry scoped unchanged accepted decisions and closed findings with their evidence, and open findings requiring explicit dispositions. Permit reopening on real counterevidence, changed dependencies or demonstrated invalid closure; preserve the finding ID, reason, current hashes and independent reviewer evidence. Give the reviewer the current target, criteria and relevant originals/model, but no desired verdict or protected evaluation answers. Submit the reviewer's actual output through `submit` first, then invoke `review` with its actual returned review and identity. The review request binds both the target `attempt_id` and the reviewer's `review_task_attempt`, plus current target hashes. The producer may respond or revise but may not impersonate the reviewer, close its finding or author its approval.
8. Inspect `status` after submissions/reviews. Route real findings to responsible owners, issue fresh attempts when needed, and `export` the actual current plan/execution/evidence package. Export is not an assertion of production quality. Where supported and authorized, dispatch the separate independent quality-evaluation work, submit its actual artifacts, and use installed `quality` and `finish` operations only with real evidence satisfying the protected profile. Read their exact `--help` and schema. Ordinary review plus export is insufficient for final completion. The currently provisional `valuation-v1` evaluator blocks final completion pending calibration: export the allowed draft/current state and report that gate, never invent calibration or quality scores.


## Skill contract preservation

Before registering a node, read every bound skill's `contract.json`. The union of its `acceptance` (or `validations`) IDs must be included in `node.required_checks`; its `consumes` must be included in `node.consumes`; and its `outputs` must be included in `node.outputs`. Preserve domain rule output names too. Multiple skills may share a physical output packet, but every declared output type must remain represented in the submission, with distinct artifact names and precise section/key locators where needed. A domain alias does not silently replace a required skill output type. Bind fewer skills when their full contracts are unnecessary; never remove checks just to simplify a node. Only actual observed checks can pass. Unperformed or unsupported required work remains failed/not-run or a capability gap.

## Settings and receipt integrity

Record requested, host-resolved and execution-observed model/effort independently. Unreported values remain `null` with an unavailable reason. A sent spawn option proves only what was requested. Do not infer settings from model names, latency or writing quality. Native host ids and retained receipts provide cooperative audit evidence, not cryptographic proof of identity or a human signature.

Do not overwrite input artifacts, old outputs or a pinned installation to make a result fit. Report stale-attempt, hash mismatch, unsupported capability and missing independence as their actual states. Continue only still-active same-task workers through supported actions with intact bindings; new tasks and completed workers require fresh attempts/actors. Do not manufacture a token or edit a ledger.

The native bridge binds actual agent ids and receipt hashes attested by the host as cooperating-process integrity. This is not cryptographic identity authentication. Preserve the host attestation and raw receipt as required by the installed schema; never fabricate an attestation. The provisional `valuation-v1` protected evaluator blocks final completion pending calibration. A valid plan or exported draft cannot bypass that gate.

## Session observations

The versioned `session-policy.json` records operational guidance, not native tool enforcement. Prepare a handoff at 10 observed tool calls; hand off at 15 calls or 100,000 last-input tokens. Unknown usage is unknown, not zero. Prompt/summary/tool-summary bounds are 8,000/1,000/4,000 characters; persist raw output before any summary. Image inspection uses at most two images per batch and five pages per session, with all pages covered for the first document. Split work across fresh sessions without dropping coverage. Main-role sessions (meta, PM, coordination and integration) are separate tasks; bookkeeping cannot reset the actual parent conversation or report intake clock.
