# FDD planning policy — 0.1.0-dev.1

## fdd-rule-planning — Transaction-specific inquiry

Establish buyer-side, vendor-side or public-data screening purpose, acquired perimeter, cutoff, transaction stage and actual access. Unknown contractual terms remain unknown; do not infer a locked-box or completion-accounts mechanism. Define the transaction decision each inquiry could change.

Plan quality-of-earnings work against monthly ledger/trial balance, invoices, credit notes, contracts, projects and cash collections. Reconcile population coverage to reported totals before proposing samples. Test revenue cutoff, returns, rebates, capitalization, related parties and recurring supposedly exceptional costs. Distinguish historical normalization, prospective improvements and buyer-specific synergies; identify replacement costs and contrary evidence.

Plan seasonal working-capital analysis across the operating cycle, with ageing, billing milestones, inventory, supplier terms and temporary collection/payment actions. A year-end balance is not automatically a suitable peg. Plan debt-like/cash-like classifications against actual transaction definitions, leases, factoring, restricted cash, tax and contingent liabilities. Track stable exposure IDs across earnings, working capital and debt so one item is not counted twice. Do not turn an earnings adjustment into purchase-price impact without the actual valuation and contractual mechanism.

Return fdd-research-plan and fdd-access-and-capability-gaps as the exact planned node output names. Each work item has a question, population, source request, procedure, accountable capability, evidence acceptance condition and conclusion limit. Review roles source/judgment cover the plan and access assumptions, not completed diligence. Denied access remains an access limit, not a clean finding.

## fdd-policy-production-block — Planning-only boundary

execution_support is planning-only and production_quality_verified is false. The engine must reject report-mode selection. This version does not execute FDD, establish reviewed adjusted earnings/NWC/net debt, provide assurance or negotiate price. Development/planning work may define these tests; a completed engagement requires a future supported execution contract and actual domain evidence/review. Do not reuse valuation report execution to bypass this boundary.

Component refs are exactly {id, version, sha256}; requires contains string IDs. Stable component/rule/clause IDs are retained across meaning-preserving revisions, never reused for a new responsibility. Main owns meta-orchestrator, codex-native and protected evaluations. Rule semantics: unconditional coverage requirement; capability, review-role and artifact names must appear in actual plan nodes. Plan coverage is not performance or approval.
